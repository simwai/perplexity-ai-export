# Failure Guards

Use this module to detect and handle protocol breach.

## Breach conditions

A protocol breach has occurred when:

- a response contains content from more than one phase
- !!! a patch is emitted without an approved plan
- !!! a patch is emitted without a complete rewrite contract
- the phase header is missing (in `STRUCTURED` mode only; `DIRECT` mode uses `[MODE: DIRECT]`)
- a later-phase action is taken in response to a user request without phase transition
- review findings are emitted without a checklist artifact
- docs-dependent judgment is emitted without docs evidence
- a consolidated report claims complete coverage while a file or batch is missing, failed, or unrecorded
- a consolidated report presents provisional findings as user-accepted
- consolidated mode advances to PLAN without explicit aggregate confirmation
- a read step repeats with an identical fingerprint three consecutive times without an intervening state change (doom loop, see module 31)
- a REVIEW verdict is issued without verification evidence or a recorded H11 exclusion
- a phase response is emitted whose phase-specific modules from `12-module-routing.txt` are not loaded/recorded (skipped module load)
- a credential-bearing file (`.env`, `.env.*`, `secrets/`, `*.pem`, `*.key`)
  was read with the read-file tool, or its raw contents entered the transcript
  (H1, modules 32/15)
- `git remote -v` output or any remote URL entered the transcript unsanitized
  (H1, module 33)
- !!! a commit or push is executed without the module-33 ask when the session made file edits
- !!! files outside the session's edited-file set are staged for the gate commit
- on a confirmed `READ_ONLY` host (module 34): a mutating git operation, a
  `SESSION_STATE-*.md` write, or a diff-only delivery where the Delivery
  contract requires complete file contents
- !!! a `SPECS/` write (new spec, registry row, or spec-body edit) occurs outside PATCH (module 35 write governance)
- !!! a HALT bypass: version drift resolved silently, or a BLOCKED-variant emitted in place of the DRIFT-internal decision block (modules 35/36)
- !!! an adversarial-gate bypass: the devil's-advocate pass skipped before REVIEW decision confirmation or PATCH conclusion (modules 01/24/25/27)
- !!! a DRIFT phase output performs a write (module 36 read-only posture)

## Recovery rule

1. Identify the last valid phase.
2. Return to that phase.
3. Output only the allowed template for that phase.
4. If the next response breaches again, terminate with FAILURE.

## FAILURE trigger

!!! FAILURE is triggered when:

- one recovery attempt already failed
- the next response breaches protocol again

## Post-failure rule

!!! After FAILURE:

- Do not continue until the user explicitly requests a retry.
- Emit only the FAILURE template while waiting for that retry request.
- On an explicit retry, resume from the recorded last valid phase.
- A post-FAILURE retry resumes from the last valid phase without requiring the
  re-loading of modules already present, and without forcing a `BLOCKED` phase to retry.
