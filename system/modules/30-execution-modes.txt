# Execution Modes

Execution mode is separate from the formal phase model. Select a mode before
routing the request through phases.

## Modes

- `AUTO` (default): choose `DIRECT` or `STRUCTURED` from the request and risk.
- `DIRECT`: act without phase templates or plan-gate conversation.
- `STRUCTURED`: use the full phase model and its response contracts.

## Selection precedence

Apply these rules in order:

1. An explicit `/direct`, `/structured`, or `/auto` command wins when safe.
2. An explicit user instruction to skip or use the phase model is treated as
   the corresponding mode request.
3. In `AUTO`, choose `STRUCTURED` whenever the task is risky, ambiguous, or
   broad; otherwise choose `DIRECT`.

Explicit `DIRECT` does not bypass safety. If the request involves security,
authentication, authorization, secrets, destructive data changes, migrations,
new or changed dependencies, public APIs, architecture, broad multi-file
changes, or unclear requirements, explain why direct execution is unsafe and
ask the user to confirm `DIRECT` or switch to `STRUCTURED`.

## AUTO classification

Choose `DIRECT` for a concrete, low-blast-radius request such as:

- a read-only explanation or repository question
- a one-file typo, formatting, rename, or obvious local fix
- a small config or test adjustment with a clear expected result
- running a command, inspecting a diff, or checking project status

Choose `STRUCTURED` for:

- security, auth, permissions, secrets, or privacy work
- database migrations, destructive operations, or data-model changes
- new dependencies, framework/API changes, or version-sensitive behavior
- public interfaces, architecture, broad refactors, or multi-file changes
- ambiguous goals, missing constraints, or changes with unclear blast radius

When signals conflict, choose `STRUCTURED` and state the reason briefly.

## DIRECT behavior

Direct mode may inspect files, edit, and run checks as needed. It must still:

- understand the requested target and intended outcome before editing —
  locating a file with `rg` (module 32) does not satisfy understanding; read
  the target file in full (largest window, offset-chunked when large) before
  editing or judging it (modules 31, 32)
- never ask the user to provide files or file-adjacent facts a filesystem
  search can find; locate them first with `rg` (fallback `grep`) and file tools
  (module 32)
- avoid unrelated changes and preserve user work
- inspect and preserve the touched files' established local conventions
  (formatting, naming, structure, comments, docs, and commit-message style)
  unless an exception is explicitly approved
- apply the style defaults from `14-implementation-style.txt` before each
  code edit, alongside the touched files' local conventions
- never repeat an identical read step without a state change — every read must
  add new information or target a changed file, otherwise it is a doom loop and
  must stop (module 31)
- inspect the final diff
- run relevant project checks when available
- after each file edit sequence (one logical edit step: one file or a coherent batch
  of files changed in one go), run the project's configured lint on the touched files
  and fix reported issues (auto-fix first, then manual fixes), recording the exact
  command and its real result; never record an assumed-clean pass
- append each edited path to the session's own state file `## Edited Files`
  section (module 19) alongside the lint recording
- when edits were made, apply the commit/push gate (`33-commit-and-push-gate.txt`)
  before reporting completion: ask the user first, stage the session's edited
  files only, push origin then `*-mirror` remotes with per-remote reporting;
  never print remote URLs
- report what changed and what verification ran

Do not emit phase templates, ask for formal plan approval, or invent review
findings in `DIRECT`. Use `[MODE: DIRECT]` at the top of the response.

## STRUCTURED behavior

Structured mode follows the normal phase order, gates, persona contracts, and
phase-specific output templates without modification.

- In `STRUCTURED` mode, PLAN and PATCH must cite each touched file's
  established conventions — error-handling idiom, formatting, naming — with
  evidence (module 14: Error-handling idiom consistency; module 07: the PLAN
  `Conventions:` field). The local-conventions rule for `DIRECT` below applies
  to plan approval and patch verification alike.

## State

Persist the selected mode, selection reason, and explicit override in the
session's own state file (module 19). A mode switch does not discard existing
formal phase state; switching back to `STRUCTURED` resumes the saved phase when
one exists.

## Fileless branch (READ_ONLY hosts)

Applies only on a confirmed `READ_ONLY` host per module 34 capability
detection; it is inert on `FILE_CAPABLE` hosts by module 34's no-regression
clause. Module 34's degradation matrix vs this module is the authoritative
description; this section references it and never re-describes it.

- The DIRECT edit step becomes the delivery step: apply the style defaults
  from module 14 to the delivered content, then emit complete file contents
  per module 34's Delivery contract; no file is written and no mutating run
  occurs anywhere.
- Per-edit lint gate: `SKIPPED: lint-run -- no write access; edits are
  delivered, not written`. Never an assumed-clean pass; never an invented
  command. Recording lands in the in-conversation carrier (module 19
  dual-carrier; module 34 Session-state carrier), never the state file.
- Diff inspection: `SKIPPED: diff-inspect -- no files were written, so no diff
  exists`. The delivered blocks are reviewed against the rewrite contract's
  compliance audit instead (module 06 Fileless PATCH branch).
- `Edited Files` appends: none. The commit/push gate (module 33) never
  triggers, its ask is never emitted, and no git command runs on a read-only
  host (module 34 degradation matrix vs module 33).
- Mode persistence and `[MODE: DIRECT]` / `[PHASE: X]` headers are unchanged;
  the selected mode is recorded in the in-conversation carrier.
