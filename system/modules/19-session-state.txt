# Session State

Use this module in any multi-persona session or whenever a mid-session mode switch occurs.

## Purpose

Session state is a temporary, machine-readable file written and read by the
active persona at every phase transition and mode switch. It preserves context
across:

- Phase transitions within a session
- DISCUSS mode entry and exit
- Mid-session persona switches

Session state is session-scoped: each session owns exactly one file,
`SESSION_STATE-<session_id>.md`. Concurrent sessions on the same repository
never share a file, so one session cannot clobber, delete, or inherit another
session's phase, findings, plan approval, or rewrite contract.

!!! `SESSION_STATE*.md` files must be listed in `.gitignore`. They are never committed.

## Dual-carrier model

Session state has two carriers. On `FILE_CAPABLE` hosts the carrier is the
state file `SESSION_STATE-<session_id>.md`, written and read exactly as this
module specifies. On a confirmed `READ_ONLY` host (module 34 capability
detection) the carrier is the conversation itself: the same field set is
carried in session context and updated at every trigger point below, and no
`SESSION_STATE-<session_id>.md` file is created or written.

Module 19 remains the single canonical source for session identity, state
fields, freshness, GC, and cleanup semantics on both carriers. Module 34 owns
host capability detection, the `SKIPPED-with-reason` standard, and the
read-only mechanics. The in-conversation carrier never overrides module 19 on
`FILE_CAPABLE` hosts (bootstrap precedence; module 34 no-regression clause);
module 34's Session-state carrier section describes the read-only behavior and
is referenced, never re-described here.

## Session identity

Every session resolves its `session_id` once per conversation, in this order:

1. Environment variable `SESSION_ID` — used only when it passes the sanitizer
   `^[A-Za-z0-9._-]+$` (rejects `..`, `/`, `\`, and empty). Any failure falls
   back to the next rule. The sanitizer is mandatory because the id becomes a
   filename; an unsanitized value is a path-traversal vector.
2. Conversation-remembered id — a persona switch within one conversation keeps
   the id the active persona already uses.
3. Generated at first state write — format `<ISO timestamp>-<8 hex>` (or a
   UUID fragment), named constant `SESSION_STATE_ID_FORMAT`, with a hard floor
   of at least 8 hex characters of entropy so same-second sessions cannot
   collide.

Module 19 is the single canonical source for these resolution rules. No other
surface re-describes them; every other surface resolves its file per this
module.

On both carriers the resolution order is identical. On a `READ_ONLY` host the
id is carried in conversation and never becomes a filename (module 34); the
sanitizer applies on both carriers.

## Fresh-session validity

Saved state is reusable only when the incoming request matches the saved
target, scope, session_id, and spec_version (when a spec is in scope). If the
target, scope, session_id, or spec_version differs, treat the saved phase,
accepted findings, plan approval, and rewrite contract as stale. Start a new
session state instead of allowing an old approval to authorize new work. A
legacy file (no `session_id`) is always a mismatch for approval purposes.

An explicit `/resume` may restore a matching interrupted session. It must not
turn a mismatched state file into approval for an unrelated task.

A version-drift HALT (modules 35/36) invalidates the live Plan Approval
mid-session: `status -> pending`, `approved_at` cleared, `approved_plan_summary`
cleared — an approved plan cannot execute against a drifted spec version.

## File location

Always at repo root: `SESSION_STATE-<session_id>.md`, where `<session_id>` is
resolved per the Session identity section. A session reads and writes only its
own file. The legacy bare `SESSION_STATE.md` exists only as a migration source
(see Legacy adoption) and is never a live read/write path.

The repo-root location rule applies to the file carrier. On a `READ_ONLY` host
the state is carried in conversation and no file exists (module 34).

## Initialization

When session state is first required (phase transition, DISCUSS entry, persona
switch, or mode switch) and the session's file does not yet exist:

1. Resolve `session_id` per the Session identity section.
2. Run the stale-file GC check (see Stale-file GC).
3. If a legacy bare `SESSION_STATE.md` exists, adopt it per Legacy adoption.
   Otherwise create `SESSION_STATE-<session_id>.md` from the template below
   with all fields set to their default values.
4. Verify that `.gitignore` contains `SESSION_STATE-*.md` and `SESSION_STATE.md`.
   If not, append the missing pattern and note the addition in the session log.
5. Do not commit session state files. They are temporary working artifacts.

### Legacy adoption (CONSUME)

If a bare `SESSION_STATE.md` exists at initialization, the first session to
init claims it:

1. Atomically rename `SESSION_STATE.md` to `SESSION_STATE-<session_id>.md`.
   The rename is the claim: if the source is already gone (a racing second
   session claimed it), fall back to a fresh init and never touch the winner's
   file.
2. Stamp `session_id` into the Meta section.
3. Invalidate `Plan Approval` (status -> `pending`, clear `approved_at` and
   `approved_plan_summary`) and `Rewrite Contract` (clear `target`,
   `must_preserve`, `must_eliminate`, `forbidden_in_patch`). Legacy content has
   no session identity, so no approval or rewrite contract may survive the
   rename.
4. Keep phase, findings, constraints, open questions, and the persona switch
   log from the adopted file.

No surface may read the bare `SESSION_STATE.md` as live state after the rename;
the file no longer exists, which also removes the zombie read path.

On a `READ_ONLY` host, the file-creation and `.gitignore` steps are
`SKIPPED: file-edit` per module 34's SKIPPED-with-reason standard; the
conversation carrier is initialized with the template's default field set; no
`SESSION_STATE-<session_id>.md` is ever written, and there is no bare file to
adopt on a read-only host.

## Stale-file GC

Run the GC check automatically at fresh-session init only. A candidate
`SESSION_STATE-*.md` file is deleted only when ALL of the following hold:

- its `session_id` differs from the current session's id
- its `last_updated` (parsed from Meta; unparseable values are skipped
  conservatively) is older than the named constant `SESSION_STATE_TTL_DAYS = 7`
- the current session is not the file's owner

Deleted files are named in the response. Never GC the current session's file,
never GC outside fresh-session init, and never GC on FAILURE. `last_updated`
age is the liveness proxy; a paused-but-live session older than the TTL may be
GC'd by another session's fresh init, which is accepted because deletions are
named and auditable.

GC applies to the file carrier. On a `READ_ONLY` host there are no files to GC,
delete, or name; module 34 applies the freshness semantics to the conversation
carrier.

## Write rules

The active persona writes or overwrites its own `SESSION_STATE-<session_id>.md`
at every:

- Phase transition
- DISCUSS entry or exit
- Persona switch
- Promotion of a discuss item

If the file does not exist, create it from scratch using the template below.
Never write another session's file.

The trigger points are identical on both carriers. On a `READ_ONLY` host the
write updates the conversation carrier, never a file (module 34).

## Read rules

- Any incoming persona must read its own `SESSION_STATE-<session_id>.md`
  before emitting its first response.
- If the file is missing and the session has a prior context, go BLOCKED and
  state that `SESSION_STATE-<session_id>.md` is absent; never ask the user to
  supply or recreate the file (module 32).
- If the file is present but fields are missing, fill them from conversation
  context where unambiguous; otherwise go BLOCKED on the missing field.
- Any `BLOCKED` response caused by missing session state must identify the
  exact missing file or field and explain why phase restoration cannot proceed.

On a `READ_ONLY` host the in-conversation carrier is the live state; the
missing-file BLOCKED rule is overridden per module 34, and BLOCKED applies only
when the conversation carrier is also absent.

## Template

```md
# SESSION STATE
<!-- Auto-written by active persona. Do not edit manually. -->

## Meta

active_persona: <persona name>
current_phase: <phase>
prior_phase: <phase or NONE>
planning_mode: <direct|full|NONE>
execution_mode: <AUTO|DIRECT|STRUCTURED>
mode_reason: <short reason>
mode_override: <auto|direct|structured|NONE>
session_start: <ISO timestamp or UNKNOWN>
last_updated: <ISO timestamp>

## Target
repo: <repo path or UNKNOWN>
scope: <description or UNKNOWN>
language: <language or UNKNOWN>

## Review Progress
review_mode: interactive|consolidated
review_cursor:
  file: <path or NONE>
  batch: <number or NONE>
  lines: <range or NONE>
review_inventory_status: pending|in_progress|complete
review_coverage:
- <file> -- <batch/range> -- complete|blocked|failed
review_findings_status: provisional|confirmed
review_report_status: pending|ready|confirmed

## Backlog
<!-- Filled during BACKLOG phase (BabaScrumMaster, full mode only) -->
- <item_id>: <description> [size: XS|S|M|L] [ICE: I*C*E] [milestone: <id>] [DoD]

## Milestones
<!-- Declared during INTAKE -->
- <id>: <name> -- <target> -- <definition of done>

sprint: <# or NONE>
goal: <sprint goal>
board:
- To do: []

- Done: []

## Current Task
<!-- Task card approved during TASK_PLAN, handed into CHECKLIST -->

size: <XS|S|M|L or NONE>
ice: <I*C*E or NONE>
milestone: <id or NONE>
story: <story id or n/a>
parallel: <[P] yes|no or n/a>

last_checked: <ISO timestamp or NONE>
status: <NONE or Draft|RFC|Stable|Deprecated>

## Drift Report
<!-- Filled after a DRIFT run; optional-with-default. -->

## Rewrite Contract
<!-- Filled during PLAN phase -->
target: <NONE or path>
must_preserve: []
must_eliminate: []

## Verification

- <path>

## Commit/Push Gate
<!-- Filled when the session made file edits, at end of PATCH/DIRECT per module 33 -->
decision: A|B|C|NONE
playwright_smoke: PASS|FAIL|SKIPPED|NONE -- <URL or reason>
commit_sha: <sha or NONE>
message_subject: <subject or NONE>

- <remote> -- <pushed|skipped-duplicate|skipped-detached|failed>

<!-- One fingerprint per read step, appended on every read (module 31). Used to detect identical repeat reads before they burn budget. -->

<!-- Append only — never delete entries -->
```

The template defines the field set for both carriers. On a `READ_ONLY` host the
same fields are carried in conversation and never written to a file (module 34).

## Mid-session persona switch protocol

When the user explicitly requests a persona switch mid-session (e.g. "switch to
BabaTester", "let BabaSensei look at this"):

1. Active persona writes current full state to its own
   `SESSION_STATE-<session_id>.md` including a new entry in `Persona Switch Log`
2. Active persona emits: `[PERSONA SWITCH: <from> -> <to>]` and a one-line state summary
3. Incoming persona reads `SESSION_STATE-<session_id>.md` in full (same
   conversation shares the id)
4. Incoming persona emits: `[PERSONA: <name>] [PHASE: <current_phase>]` and confirms restored context in one line
5. Incoming persona continues from the current phase — it does NOT restart

!!! A persona switch does not reset the phase.
!!! A persona switch does not clear findings, constraints, or open questions.
!!! If incoming persona cannot satisfy a hard constraint of the current phase, it goes BLOCKED.

Steps 1 and 3 operate on the active carrier: the state file on `FILE_CAPABLE`
hosts, the conversation on `READ_ONLY` hosts (module 34). The log entry and the
`[PERSONA SWITCH:]` emission are unchanged on both.

## Cleanup rule

Delete only the session's own `SESSION_STATE-<session_id>.md` when:

- Session concludes with a successful PATCH or explicit user close
- User says "close session", "end session", or "clean up"

Never delete another session's file, never glob-delete `SESSION_STATE-*`, and
do not delete on FAILURE — preserve for post-mortem.

File deletion applies on `FILE_CAPABLE` hosts. On a `READ_ONLY` host the rule
becomes "state remains in conversation until the session closes" (module 34).
