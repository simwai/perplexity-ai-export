# MCP Invocation Decision Guidance

Use this module in every phase, every persona. Tool selection is a per-response decision: built-in tools first, MCP only to fill an evidence gap.

## Mandatory session setup and preflight

Before the first invocation of any MCP server in a session, inspect whether that
server is configured for the current environment. If it is not configured, set
it up in the current session before checking readiness. Do not invoke the
server's task operation before setup and verification complete.

- For a local server, inspect its configured command, package/runtime, and
  required environment. Automatically install a declared dependency, create a
  missing non-secret local config, and start the server when those steps are
  safe and deterministic. Then use a harmless health, metadata, or list
  operation if the server exposes one.
- For a remote server, verify that the connection is available and required
  authentication is accepted. Complete non-interactive setup automatically;
  pause only when an API key, OAuth consent, account action, or other user
  authorization is required. Never invent credentials or send task data during
  setup.
- If setup requires a project-file change, make it only when the server's
  documented configuration and target are unambiguous; otherwise report the
  exact missing setup step and ask for confirmation.
- Record one result per server in the session's MCP preflight ledger as
  `ready`, `unavailable`, or `not_checked`.
- A successful preflight is valid for the rest of the session. Do not repeat it
  for every call unless the server fails, its configuration changes, or the
  session changes environment.
- If setup or the preflight fails, do not make the requested MCP call. Apply the
  fallback ladder below and record the failure; never treat an untested server
  as ready.

When the session's own state file is active (module 19), persist the setup and
verification evidence in its `MCP Preflight` section. Otherwise keep the ledger
in session context and report the setup and preflight result when MCP is used.

## Signal -> tool matrix

| Signal | Tool | Setup |
|---|---|---|
| Official/versioned library, framework, SDK, or API docs needed | `context7` | remote, no key |
| Current web info beyond docs (news, RFCs, pricing, ecosystem landscape) | `exa` / direct `curl` | env key / no key |
| Unknown dependency/API name or version discovery | `exa` / direct `curl` | env key / no key |
| Work tracking: cards, boards, lists, tasks, PR/issue/CI status | `trello` | remote OAuth |
| Live browser: navigate, click, fill, screenshot, UI verification, e2e walk-through | `playwright` | local, no key |
| Approved mitigation's verification step requires a live browser (e.g. screenshot the affected UI flow, click through a fixed element, snapshot the corrected route) | `playwright` | local, no key |

## Phase pairing

- `CHECKLIST`: no MCP unless the task references Trello cards/boards.
- `DOCS`: `context7` primary (official source, exact version); `exa`/`curl` for discovery. MCP output is evidence input only — the DOCS template fields (name, version, URL, changelog window) must still be recorded per module 03.
- `REVIEW`: `playwright` when the target is a web app needing live UI checks; `trello` when review scope references tracked work.
- `TEST_STRATEGY`: `playwright` for e2e/UI exploration and verification.
- `PLAN` / `PATCH`: `trello` for tracked-task status updates; `playwright` for
  verification, including the pre-commit functional smoke in the module-33 gate,
  the approved-mitigation verification step (a mitigation whose primary action
  is a browser-based check -- e.g., "re-test the form submission flow" --
  uses Playwright as its verification tool, preflight per the session setup
  section above), and any REVIEW H11 e2e smoke; otherwise built-in tools.
- `REVIEW`: decision lives in this phase; no separate CONFIRM MCP pairing.
- `DISCUSS`: MCP allowed for exploration, but never emits findings without explicit user promotion (module 18).

## No-go rules

- If built-in tools (`read`, `grep`, `glob`, `bash`) can answer from local context, do NOT invoke an MCP.
- Bounded deep-dive budget: up to 3 targeted lookups per dependency per DOCS
  phase (matches the context7 harness cap), each mapped to a named evidence
  gap — no exploratory firehose. Each lookup must use a distinct fingerprint
  (module 31) and cite the section it answers (module 03). Beyond the budget,
  extend via the fallback ladder, never by repeated calls.
- Never re-invoke a lookup whose fingerprint already produced a result in this
  session — check the session read ledger (module 31) and reuse the recorded
  result instead of repeating the call.
- Never send secrets, tokens, or proprietary code through remote endpoints (`context7`, `exa`, `trello`) — H1 guard.
- `playwright` `browser_run_code_unsafe` is RCE-equivalent — trusted sessions only, never run untrusted code.
- The pre-commit gate smoke (module 33) uses safe browser tools only
  (`navigate`/`click`/`fill`/`snapshot`/`screenshot`), never
  `browser_run_code_unsafe`; when the repo declares no web-app entry point the
  smoke is SKIPPED with reason, never invented.

## Web search without keys

General web lookup must never require `GOOGLE_API_KEY` / `GOOGLE_SEARCH_ENGINE_ID`. Default is direct curl to Google's URL format:

```bash
curl -s "https://www.google.com/search?q=<url-encoded-query>"
```

## Fallback ladder

1. MCP setup or preflight fails (server missing, local setup broken, key absent, OAuth declined) -> fall back, do not stall.
2. Deep-read ladder for official docs (module 03), in order:
   a. Fetch the docs TOC / sitemap / sidebar to enumerate candidate sections.
   b. Fetch the section page that maps to the in-scope criterion.
   c. Fetch the exact anchor (URL fragment) that supports the claim.
   Each step uses `curl` to the official source URL or direct web search
   (above); the ladder ends at the last step that yields new evidence.
3. If evidence still cannot be verified -> `BLOCKED` with a specific reason
   naming the unavailable evidence and explaining why the dependent phase cannot
   proceed. Record the explicit unresolved-version note per module 03. Never
   guess a version or URL from memory.
