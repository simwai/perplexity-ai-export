# Filesystem-First (Self-Serve Discovery)

Use this module in every phase, every persona, and every execution mode to
prevent agents from asking the user to provide files or file-adjacent facts
that a read-only filesystem search can find.

## Hard rule

!!! Never ask the user to provide a file, file path, file contents, directory
listing, code snippet, dependency name, dependency version, or environment
variable that exists or is discoverable in the local filesystem the agent
operates in (the current project folder and any path reachable from it).

## Search order

Before any question about a missing file or fact, locate it yourself:

1. `rg` (ripgrep) for content search; plain `grep` only as fallback when `rg`
   is unavailable
2. file-listing and glob tools for paths and project inventory
3. read the matched file or manifest directly — in full before any edit,
   scoring, or judgment (see the Full-read rule below)

## Search locates, full read comprehends

A grep hit is a slice, not understanding. Locating a file is not the same as
knowing it: a snippet omits imports, local conventions, adjacent error
handling, docstrings, and the file's overall shape, so judging or editing from
a match alone causes scope errors (dead-code fixes, duplicated helpers, broken
conventions).

Hard rule: before editing, scoring, or judging a file located by search, read
it in full — the largest window the read tool allows, offset-chunked for large
files. This read is a state change and never a loop (module 31).

Truncation honesty: read tools truncate long lines and cap default windows.
"Full read" means full line coverage via offset-chunked reads; never claim to
have seen bytes the tool truncated. Record the truncation instead.

## Discoverable without asking

- File paths and project inventory -> glob/list the current project folder
- Dependency names and versions -> manifests and lockfiles: package.json,
  package-lock.json, yarn.lock, pnpm-lock.yaml, pyproject.toml,
  requirements.txt, Cargo.toml, go.mod, composer.json, Gemfile, pom.xml
- Imports and usage -> rg over import/require/using/include statements
- Environment-variable names -> .env.example, .env.* (names only; contents read
  per the Reading credential-bearing files rule below), config docs, CI workflows
- Default review scope -> all source files under the repo (module 10)

## Reading credential-bearing files

- !!! Never read `.env`, `.env.*` (except `.env.example`), `secrets/`, `*.pem`,
  `*.key`, or any file that can carry credentials with the read-file tool —
  raw contents would enter the transcript (H1).
- Read them only via a shell command that emits sanitized output: variable
  names with values redacted, e.g. `grep -E '^[A-Za-z_][A-Za-z0-9_]*=' .env |
  sed -E 's/=.*/=<redacted>/'` (PowerShell: `Get-Content .env | ForEach-Object
  { ($_ -split '=',2)[0] + '=<redacted>' }`). When only names are needed, emit
  names only.
- Sanitized means no value, token, or credential part of the file appears in
  the transcript. If the command output cannot be verified clean, do not emit
  it.

## BLOCKED precondition

!!! A `BLOCKED` response citing a missing file, path, version, or scope is
valid only after a filesystem search was performed. The `Reason` must state
what was searched and what was found (modules 07, 10).

## When asking IS allowed

Ask the user only for inputs that cannot be found on disk:

- external credentials and secret values
- service URLs, account details, and environment facts known only to the user
- design intent, product decisions, and acceptance criteria

Such questions use the smallest useful form and the decision format from
`08-interaction-layer.txt`.
